# AI log

What Claude Code got wrong, assumed, or changed, and how it was caught. One or two lines per entry, newest last.

---

- **2026-10-14, Step 0.1 (environment).** Plain `uv add numba` picked the newest Numba (0.68), whose llvmlite 0.50 has no Intel-Mac build; uv tried to compile it and failed. The plan had predicted this (Phase 0, "What can go wrong"). Fixed by pinning `numba>=0.62.1,<0.63`, the last line with Intel-Mac wheels (checked on PyPI); recorded in `docs/DECISIONS.md`.
- **2026-10-14, Step 0.1 (commit).** First commit missed files: `runs/` in .gitignore also hid `configs/runs/` (fixed with root-anchored `/runs/`), and `reference/expected-values.md` was absent (the wrong one of two identical copies had been removed during cleanup; the survivor was moved back into `reference/`). Caught by listing the committed files before moving on.
- **2026-10-14, Step 0.4 (GPU check).** Claude's first test shader kept a running float32 sum of 2,000 values; GPU and CPU then differed by 4.2e-5 (tolerance 1e-5). A float64 comparison showed both were equally off the true value (2.9e-5): float32 accumulation error in the test design, not a GPU bug. Fixed the code, not the tolerance: block summation (50 × 40) on both sides → 1.5e-6. Lesson for Phases 2, 8, 9: long float32 accumulations on the GPU need care. Also: pytest collected a helper named `test_pattern_reference` as a test; renamed and set `testpaths = ["tests"]`.
- **2026-10-14, Step 0.5 (video).** Claude's first writer used ffmpeg's `-colorspace/-color_primaries/-color_trc` output flags; the file came out tagged `bt709/unknown/unknown` (primaries and transfer missing) while its own format test passed, because it only checked that "bt709" appeared somewhere. Fixed with a `setparams` filter before conversion and a stricter tag check. Added an independent colour test (decode the YUV by hand with the BT.709 formula), checked to fail on ffmpeg's default BT.601 conversion. Claude first told Hiten the old flags also shifted colours by 25 levels; a check showed that applies only to no colour settings at all, and the claim was corrected. The new test itself first had a uint8 wrap-around bug (impossible "542 levels"), fixed by converting to float.
- **2026-10-14, Step 1.2 (gravity).** Two tests first failed although the physics was right: Claude's `check()` measured relative error per x/y/z component, so a near-zero component (3,000× smaller than its vector) made a 4e-16 round-trip error look like 8e-14. Diagnosed by comparing per-vector and per-component errors; fixed by adding a per-vector comparison (tolerances unchanged; recorded in DECISIONS.md). The key independent test (Euler–Lagrange by finite differences of the paper's Lagrangian) passed first time and was shown to catch three planted typos.
- **2026-10-14, Step 1.3 (orbits).** Claude computed the end angle of the orbit integral with `arccos`, which loses ~√ε ≈ 1e-8 at the apocentre (infinite slope at θ = π). All §2 expected-value tests still passed (they need 1e-8), so only Claude's extra cross-check against the closed-form elliptic integral caught it: errors up to 4.4e-7 on near-circular orbits, with no warning from the integrator. Confirmed with a 30-digit mpmath calculation; fixed with a well-conditioned `2 atan2(...)` form (now ~1e-15). Also added a refusal for turning points that belong to no bound orbit (previously gave NaN warnings and a meaningless number).
- **2026-10-14, Step 1.4 (integrator).** Plan assumption corrected: the plan's η = 0.005 met |ΔH/H| < 1e-4 only at the end of the run (4.2e-5); the maximum during pericentre passages was 1.05e-3. Claude tested the maximum (as flagged when proposing Phase 1) and chose η = 0.00125 (max 6.4e-5), 4× more steps than planned; recorded in DECISIONS.md. Everything else matched the plan's own numbers to 4–5 digits (convergence 1.5698e-3 / 3.9235e-4 / 9.8087e-5).
- **2026-10-14, Step 2.2 (GPU rays).** Three float32 traps handled up front rather than discovered later (lesson from Step 0.4): the plan's starting-slope formula sqrt(1/b² − u0²(1 − 2u0)) cancels near ψ = 90° (Claude estimated ~2.5e-4 rad error, above the 2e-4 limit), replaced by the equivalent u0 √(1 − 2u0) cot ψ; step sizes rounded to multiples of 2⁻¹² so the running angle sums exactly; escape point found by a Hermite root inside the last step. Result: 6e-6 rad worst case for b > 1.05 b_crit (limit 2e-4), first run.
- **2026-10-14, Step 3.1 (kernels).** Claude wrote the Wendland C4 derivative as −(7/12) q (1 − q/2)⁵ (5q + 2); the correct coefficient is −7/3 (a factor-4 slip). Caught by the finite-difference test on its first run (error ~0.9 vs tolerance 1e-7). The default cubic spline was correct. Also: Claude first assumed Phantom's tabulated kernel variance was per axis; both kernels showed it is the full 3D second moment.
- **2026-10-14, Step 3.3 (density).** Two bugs in Claude's density/h iteration, both caught by tests. (1) The safeguard bracket rejected a Newton step that landed exactly on the bracket edge (strict `lo < h < hi`), so a particle already at its root jumped to bisection and needed ~40 iterations instead of 1–2; spotted from the iteration count while chasing a 2e-12 Numba-vs-reference mismatch, which dropped to 4.5e-16 after the fix. (2) An isolated particle creeping toward h_max stopped just short of it and was reported "converged"; now f(h_max) is checked whenever h ends near its limit. Claude's comparison test was also first built with neighbour lists for a smaller radius than it passed in.
- **2026-10-14, Step 3.5 (shock capturing).** Energy drifted 1.3e-4 in Claude's first 200-step run. Separated "bug vs time-step error" before changing anything: instantaneous energy rate 0 to 1e-17 for every combination of terms (no bug), error falling ~4× per halving (time-step error). The plan's 1e-6-over-1,000-steps test then needed dt = Courant/32; recorded with its caveat in DECISIONS.md rather than loosening the tolerance.
